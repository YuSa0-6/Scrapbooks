# 測り方

`pnpm build` のあと `pnpm preview --host 127.0.0.1 --port 4322` で本番ビルドを動かし、`pnpm perf`（`scripts/perf.mjs`）が `http://127.0.0.1:4322`（`BASE_URL` で変えられる）に Playwright でつないで測り、表にして出す。予算を超えたら終了コード 1。`--json` で JSON、`--strict` で「未対応」も失敗にする。

- preview は開発サーバーと同じ `.wrangler/state` を使うので、先に 4321 で `dev-bypass` をしておくと見本データが見える
- `pnpm build` のあと、起動中の開発サーバーはエラーページになる。開発サーバーを再起動する
- 長いタスクは 3 回測って一番大きい値を見る（1 回ごとに 2 割ほどぶれる）
- 詳細ページは、`/code` と `/work` の最初のカードのリンクから選ぶ（見本だけでも、好きなものを読み込んだあとでも測れる。見本の作品は下書きに戻るため、URL を決め打ちにしない）

# フォント

日本語の Web フォントは **Klee One 600 の 1 つだけ**（[fonts](/decisions/fonts.md)）。本文・ボタン・メニューは端末の日本語フォントなので、読み込むものはない。

Google Fonts の日本語フォントは、文字の範囲ごとに約 120 枚の `@font-face` に分かれて届く。全部を HTML に入れると最初のレイアウトが重くなる（3 書体のときは、HTML に 480 枚の定義（約 370KB）と 100 本超の `<link rel="preload">` が入り、CPU 4 倍で約 1.7 秒かかった）。

`config/slim-fonts.mjs` の `slimGoogle()` が、Google のプロバイダーを包んで面を絞る。

| 残す面 | 理由 |
| --- | --- |
| 半角（latin）・かな・記号 | いつも使う |
| 漢字の面のうち、よく使う順に 30 枚 | Google の面は「あとのものほどよく使う」順に並んでいる。「日」「本」「見」などは最後の 1 枚に入る |
| 捨てる面 | 残りの漢字は端末の日本語フォントで表示する（見本の文章では、足りない漢字は「廊」「肖」「拾」など数字だけ） |

- 効果：面を絞ると、HTML は 456KB → 143KB、`@font-face` は 482 枚 → 約 110 枚、preload は 119 本 → 3 本、長いタスクは約 4 割減った。書体を 1 つにすると、`@font-face` は 36 枚、HTML は約 103KB、`dist/client/_astro/fonts` は 148 ファイル → 49 ファイルになった
- 見出しのフォント（`--font-hand`）は、半角とかなの面だけ preload する（`Base.astro`）
- 新しい漢字を書いて、字が別のフォントで出るときは、`slimGoogle({ kanjiSlices })` の数を増やす

# 長いタスクの床

目標は 300ms だが、この測り方（ヘッドレス Chromium・CPU 4 倍）では届かない。日本語の文字を出すだけで床が高いため。

| 状態（表紙） | 長いタスクの合計 |
| --- | --- |
| すべての `@font-face` を外した（3 書体のとき） | 566ms |
| さらに、日本語の文字を半角の `a` に置き換えた（3 書体のとき） | 314ms |
| 3 書体（面を絞った日本語フォント） | 1200〜1450ms（作業 6）。第 3 段階の作業 1 の直前に同じ環境で測ると 1434〜1784ms |
| 面を絞る前 | 約 2200ms |
| Klee One 600 の 1 書体・面を絞る（作業 1） | 764〜791ms（3 回） |
| 好きなものを読み込んで 16 枚になった（作業 3 まで） | 764〜1081ms（5 回。予算を超える回が出た） |
| **今の実装（画面の外のカードの整形をあとまわし）** | **557〜593ms**（3 回） |

- JS は原因ではない（JS を全部止めても 1157ms だった。3 書体のとき）
- 残りは日本語の文字の整形（shaping）と、フォントが届くたびの再レイアウト。書体が 3 つから 1 つになって、およそ半分になった
- 予算は 950ms（作業 1 の 3 回の最大値 791ms の約 1.2 倍）。悪くなったことを見つける役にする。さらに下げるには、漢字の面の数（`kanjiSlices`）を減らす

## 表紙のカードの整形（作業 4）

好きなものを読み込んで表紙のカードが 16 枚になると、390px の表紙は 764〜1081ms（5 回）までふくらんだ。切り分けた結果は次のとおり。

| 実験（390px・CPU 4 倍・表紙） | 長いタスクの合計 |
| --- | --- |
| そのまま | 905〜1206ms |
| 画像を止める／フォントを止める／JS を止める | ほとんど変わらない（JS なしでも約 1000ms） |
| 背景・影・`clip-path` を外す | ほとんど変わらない（装飾は原因ではない） |
| ボードを消す | 約 200ms |
| カードの本文（`.card-body`）を消す | 約 600ms |
| 端末の日本語フォントに置きかえる | 約 600ms |

原因は、16 枚ぶんの日本語の文字の整形を、画面の外のカードまで最初にまとめて解くこと。`Board.astro` の `@media (max-width: 760px)`（格子に並べるとき）で、カードに `content-visibility: auto` を付けた。

- 画面の外のカードの整形と描画があとまわしになり、表紙は 557〜593ms になった（約 4 割減）
- 読み上げ・Tab・ページ内検索は今までどおり（Tab でフォーカスが入ると描かれる。16 枚すべてに Tab が届くことを確かめた）
- 高さの目安 `contain-intrinsic-size: auto 420px` は、1 度描かれると実際の高さを覚える。スクロール中の CLS は 0
- 描画の切り取りでテープ・ステッカー・影が欠けないよう、`overflow-clip-margin: 48px` を付けた
- 自由配置（幅 761px 以上）には付けない。3D の机・ドラッグ・View Transitions と組み合わさるため
- 動くコードの `IntersectionObserver` は、スクロールで近づくと `srcdoc` を入れる（4 個とも確かめた）
